# Kvil App Review audit

Audit date: 15 September 2026. Scope: App Store review of the iPhone app, its Watch companion and extensions, purchases, privacy, and release materials. “App preview” is interpreted as App Review; no App Store preview video is present in the release package.

**Historical baseline:** subsequent fixes, live build detachment and refreshed dark screenshots are recorded in [App Review remediation](APP_REVIEW_REMEDIATION.md). The findings below retain the evidence observed before those changes.

**CloudKit follow-up, 15 September:** the user subsequently authorized encrypted private CloudKit. The implementation replaces new KVS payload writes and retains KVS only for migration/cleanup. The full schedule, including fasting-action timestamps, remains within the encrypted payload. Production schema and signed export `2449.2.47` are verified; 129 unit tests passed. Real two-device/APNs verification and one targetless Norwegian clipping audit remain outstanding. Encryption does not establish Apple's acceptance of those fields. See [the migration report](CLOUDKIT_MIGRATION.md), [updated privacy findings](ICLOUD_PRIVACY_FINDINGS.md), and [runtime checks](CLOUDKIT_DEPLOYMENT.md). The original KVS reproduction and test/build results below have not been rewritten as results for the new transport.

## Decision at the audit baseline

**Do not submit the current candidate yet.** The current app has a missing required-reason privacy declaration, a reproduced backup data-loss case, outdated release materials, and an iCloud payload that now includes timestamps generated by fasting actions. The latter needs an explicit privacy decision before release. Three UI checks also fail repeatedly. The Release simulator build succeeds. Passing automated checks cannot guarantee first-review approval.

Source baseline: `a522939860373ae165f84e71e6ee5c77d38de753`. App source remained unchanged by the audit. Both the locally preserved App Store IPA and the live review draft use build `2446.23.21`, not the current source candidate.

## Findings to resolve before submission

### 1. P1 — Required-reason declaration is missing

**Confirmed in current source.** `LiveActivityService` uses `UserDefaults.standard` to read, write, and remove `liveActivity.lastOpening`, but the phone app's `NSPrivacyAccessedAPITypes` array is empty. Merely including `PrivacyInfo.xcprivacy` does not satisfy the requirement.

Evidence: [LiveActivityService.swift](../ios/KvilApp/Services/LiveActivityService.swift), lines 21–25 and 77–106; [PrivacyInfo.xcprivacy](../ios/KvilApp/Supporting/PrivacyInfo.xcprivacy), lines 5–6. All four source manifests were inspected. The current direct UserDefaults use is in the phone app, so the other three bundles should not receive invented declarations.

Required action: declare `NSPrivacyAccessedAPICategoryUserDefaults` with reason `CA92.1` in the phone app manifest for its own private preferences. Verify the declaration inside the final exported app. The existing release verifier checks that manifests exist; it does not audit their API declarations.

Apple's [required-reason API requirements](https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api) and [approved UserDefaults reasons](https://developer.apple.com/documentation/bundleresources/app-privacy-configuration/nsprivacyaccessedapitypes/nsprivacyaccessedapitype) support this finding.

### 2. P1 — Fasting-action timestamps cross the iCloud boundary

**Confirmed data flow; high review risk, with Apple's classification still unconfirmed.** “Break fast early” writes `adjustedOpening = now`; “Start fast now” writes `adjustedClosing = now`. These fields are inside the Codable `ScheduleSnapshot`, and `ScheduleCloudService` serializes that entire snapshot into iCloud key-value storage. There is no separate cloud representation that excludes these events. Past overrides remain in the cloud payload; the limited `forDisplay` snapshot is only used for Watch/widgets.

Evidence: [Schedule.swift](../ios/Shared/Schedule.swift), lines 56–98 and 215–266; [AppModel.swift](../ios/KvilApp/App/AppModel.swift), lines 246–250 and 375–405; [ScheduleCloudService.swift](../ios/KvilApp/Services/ScheduleCloudService.swift), lines 35–76. An isolated executable built from the production schedule engine reproduced a serialized `adjustedOpening` of `2026-09-15T07:30:00Z`; see `build/app-review-audit/payload-check.txt`. No user data was involved and no cloud request was made by that reproduction.

My assessment: these fields convey when a person said they began or ended fasting. Calling them schedule adjustments does not establish that they are outside personal health information. Guideline 5.1.3(ii) prohibits personal health information in iCloud. Even ordinary eating schedules need a defensible classification; Apple does not publish a blanket exemption for “planned times.” [Apple App Review Guidelines, 5.1.3](https://developer.apple.com/app-store/review/guidelines/#health-and-health-research).

Required action: keep user-reported fasting events out of app-managed iCloud storage, including old payloads that already contain them. Define and test the exact allowed sync fields and update the privacy text. If the product retains any health-adjacent schedule sync, document that decision and resolve its classification with Apple; consent alone does not waive 5.1.3(ii).

### 3. P1 — The submission package does not describe the current app

**Confirmed in local materials and the live App Store Connect draft.** Version 1.0.0 is Ready for Review with build `2446.23.21`. Both listing locales and the review notes still describe the older behavior.

- [review-notes.txt](review-notes.txt), line 3, says there are no start/stop controls. Current Home exposes fasting actions and undo.
- The same notes, line 9, describe separate Health opt-ins. Current `connectHealth()` requests read/write together and enables future writes when authorized.
- The English and Norwegian descriptions in [metadata.json](metadata.json) still say there is nothing to start or stop. They describe a reflection after the window closes, while current reflection eligibility is for a prior day.
- Review notes omit the current Live Activity and Siri/Shortcuts flows, guided onboarding, and days-off/break behavior.
- The local Home screenshot still shows the old Settings button, “Change today” pill, and photographic Home background. Current Home uses a date pencil, fasting actions, and a drawn landscape. All ten screenshot hashes match their manifest, but matching an old manifest does not make those screenshots current.
- The preserved IPA is `2446.23.21`, SHA-256 `b084212d3c20afca98d42e3c95c95929618d0a0641c7101b4d88239b3e737775`. Its older Health permission text confirms it is not the current candidate. The saved Apple upload/readiness records also identify this older build.
- Live English and Norwegian descriptions still advertise painted Nordic landscapes and no start/stop interaction. The draft contains four English and three Norwegian iPhone screenshots, and no preview videos.

Required action: finish the app changes, archive the exact candidate, recapture the affected screenshots and purchase review image, rewrite both listing locales and review notes around the final behavior, then upload/attach that same candidate when authorized. Read back the build association, text, and processed images. Relevant review areas are completeness and metadata accuracy, 2.1 and 2.3. [Apple App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/#accurate-metadata).

### 4. P1 — Backup validation accepts duplicate schedule IDs and loses data

**Reproduced with production validation and persistence code.** A backup containing two schedule versions with different effective dates but the same UUID passes `LocalData.validated()`. `StoredSchedule.id` has a SwiftData uniqueness constraint, so saving that accepted input silently collapses the two versions into one. The in-memory model can then disagree with what a restart loads.

Evidence: [Schedule.swift](../ios/Shared/Schedule.swift), lines 365–369, checks effective-day uniqueness but does not check schedule-version UUID uniqueness; [LocalStore.swift](../ios/KvilApp/Storage/LocalStore.swift), lines 4–11 and the schedule save loop. A standalone macOS executable compiled with the production SwiftData models printed `Validated versions: 2, distinct IDs: 1` followed by `Persisted versions: 1, round-trip equal: false`. See `build/app-review-audit/StorageProbe.swift` and `storage-probe.txt`. This was an isolated in-memory store; real app data was untouched. It reproduces the storage contract on macOS, not a complete iPhone import flow.

Required action: reject duplicate version IDs at the shared validation boundary before import replacement or cloud merge reaches persistence. Add a focused regression that exercises both rejection and preservation of existing records. The issue requires a malformed/colliding backup or sync payload, so it is less likely in a routine review walkthrough, but silent data loss prevents a reliable release recommendation. Relevant review areas: 1.6 and 2.1. [Apple App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/#app-completeness).

### 5. P2 — iCloud starts enabled, and importing a backup can enable it again

**Confirmed behavior; consent clarity needs improvement.** `Preferences.cloudScheduleEnabled` defaults to `true`. Onboarding only says the schedule “can sync”; it does not offer a sync choice. `configure()` publishes immediately. Backup restore deliberately disables Health, reminders, and Live Activities but retains the imported iCloud flag, so a backup can re-enable sync on a device where it had been disabled.

Evidence: [Reflection.swift](../ios/Shared/Reflection.swift), line 88; [OnboardingView.swift](../ios/KvilApp/Features/Onboarding/OnboardingView.swift), line 194; [AppModel.swift](../ios/KvilApp/App/AppModel.swift), lines 109–131 and 506–541.

Recommended action: make the first transmission an informed choice, preserve the destination device's consent during import, and accurately describe the enabled state. This is particularly important given finding 2. This audit does not assert that every native iCloud preference requires a custom consent screen. Relevant review areas: 5.1.1 and 5.1.2. [Apple App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/#privacy).

### 6. P2 — Live content-rights declaration is incorrect

**Confirmed in live App Store Connect.** The app uses Kayvan Mazhar's Rice Lake photo. Source attribution and an Unsplash license reference are documented in [photography/README.md](../design/photography/README.md). The live App Information page declares that the app does not contain, show, or access third-party content. [requests/content-rights.json](requests/content-rights.json) prepares `USES_THIRD_PARTY_CONTENT`, but the live value has not been corrected.

Required action: correct the live declaration for the new candidate and read it back. Retain the source/license evidence. This is a metadata discrepancy, not evidence that the photograph is unlicensed. [Apple App Review Guidelines, 5.2](https://developer.apple.com/app-store/review/guidelines/#intellectual-property).

### 7. P2 — Extreme custom schedules have no contextual safety check

**Confirmed behavior; product/review risk, not a documented Apple numeric limit.** The UI offers a one-hour eating window, and exact time editing permits a one-minute window. The production validator accepts a recurring one-minute eating window, leaving 23 hours 59 minutes between windows. Moving daily windows can create longer intervals still.

Evidence: [KvilFormComponents.swift](../ios/SharedUI/KvilFormComponents.swift), lines 107–134; [Schedule.swift](../ios/Shared/Schedule.swift), `validate(days:)`; isolated production-validator result in `build/app-review-audit/payload-check.txt`.

The app already starts with a 12:12 example and includes an adult disclaimer, suitability guidance, and a source link. It does not make disease-treatment or guaranteed weight-loss claims. Those are positive controls. Still, review the extreme-window experience with qualified health input and decide whether to limit it or provide contextual guidance. Apple does not specify a universal maximum fasting duration in its review rules; this is a risk under physical-harm review, not an assertion that 23-hour fasting automatically causes rejection. The linked [Johns Hopkins source](https://www.hopkinsmedicine.org/health/expert-qa/intermittent-fasting-what-is-it-and-how-does-it-work) is live and its 7 April 2026 update date matches the in-app attribution.

### 8. P2 — Regional declarations need a deliberate assessment

**Confirmed settings; legal applicability is not established by this audit.** The live app is declared a non-trader for EU distribution, while Full History is a paid non-consumable. Apple lists revenue through in-app purchases and commercial/professional activity among the factors to consider. A paid unlock alone does not conclusively determine trader status. Reassess and document the declaration using [Apple's DSA guidance](https://developer.apple.com/help/app-store-connect/manage-compliance-information/manage-european-union-digital-services-act-trader-requirements/); change it if the developer's actual circumstances require that.

All 175 storefronts are enabled, including China mainland, which shows “Available on App Release.” No ICP filing is configured on App Information. Apple's current documentation says filing requirements apply to some apps, so this audit does not claim a universal filing requirement for every offline utility. Resolve applicability or narrow availability before release. See [Apple's China mainland requirements](https://developer.apple.com/help/app-store-connect/reference/app-information/app-information).

### 9. P2 — Mac and Vision Pro distribution are enabled without verification

**Confirmed after the live Pricing and Availability page fully loaded.** Both “Make this app available” for Apple silicon Macs and “Make this app available on Apple Vision Pro” are checked. App Store Connect calls version 1.0.0 compatible, but explicitly says Mac compatibility has not been verified. The local build settings disable designed-for-iPhone/iPad support for Mac and XR; that does not prove the live distribution switches are off.

Required action: decide which additional platforms are intended. Verify the exact candidate on enabled platforms, including unavailable Health features and purchase/restore, or turn off those storefront options when authorized. This audit did not change either checkbox. General completeness expectations apply to every supported distribution surface.

### 10. P2 — The current UI release checks are not clean

**Three failures reproduced twice on iPhone 13 mini, iOS 27.0.** The full run and an isolated rerun of these three tests gave the same results:

| Check | Evidence and interpretation |
| --- | --- |
| `testHomeLeavesSpaceForLandscapeWithoutScrolling` | Only 90.33 points remain below Home content; the test requires 100. This is a project design assertion, not an Apple spacing rule. Review the small-phone layout and its intended minimum before changing the test or UI. |
| `testOpenWindowAndNorwegianLayouts` | Apple's automated contrast audit flags “How did yesterday go?” on open-window Home. The test exports both a full-screen and element image. Those captures look legible, so the finding is a repeated audit failure, not a claimed measured contrast ratio. Investigate the animated background and the stable rendered state before dismissing the warning. The test stops before its Norwegian follow-up portion. |
| `testReflectionProgressionAtLargestText` | The test opens the reflection sheet, then its reveal helper cannot complete the `planExperience.changed` selection. A capture during the rerun shows the feeling step while the helper is still looking for the plan answer, so gesture/automation behavior needs investigation. This does not prove the whole reflection feature is unusable. It does leave the intended largest-text changed-meal path unverified. |

Visual inspection also found the History chart's `kg` label crowded against the top `75,5` tick at the largest text size, although that chart's enclosing test passed. Inspect spacing within Swift Charts, not just its outer frame. Evidence: [WeightChart.swift](../ios/KvilApp/Features/Weight/WeightChart.swift), lines 40–49, and `History-weight-largest-text` in the exported attachments.

Required action: resolve or explain the three repeatable checks with evidence, correct the chart label spacing, and run the affected flows again. Do not weaken accessibility checks solely to make the suite green. Evidence: [test summary](../build/app-review-audit/test-summary.json), [focused rerun](../build/app-review-audit-ui-recheck.log), [contrast target](../build/app-review-audit/attachments/1737D85F-F8E0-4344-92DB-125F2E1BF114.png), [reflection at largest text](../build/app-review-audit/attachments/AB1328DB-3765-463A-B015-F323C2F04ABF.png), and [History chart at largest text](../build/app-review-audit/attachments/FF19881B-15D2-476B-8EDC-DF5E7EB82654.png). These generated artifacts are in the ignored local build directory.
